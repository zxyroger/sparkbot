# SparkBot 架构设计

面向 ESP32-S3 移动机器人的 PC 端 Agent 框架。机器人只有底盘轮子，
通过摄像头看、通过麦克风听、通过喇叭说、通过 LCD 表达情绪。

---

## 1. 为什么把智能放在 PC

ESP32-S3 有 512 KB SRAM + 可选 8 MB PSRAM，跑得动简单的唤醒词和
TFLite Micro 的小模型，但跑不动多模态大模型、语音识别和连贯的对话决策。
所以分工是：

* **ESP32-S3 做「身体」**：实时控制（电机 PID、I2S 音频、摄像头采集、
  屏幕刷新、本地唤醒词）。这些必须硬实时，且断网也要能用。
* **PC 做「大脑」**：视觉理解、语音识别与合成、对话决策、工具编排。
  这些可以容忍几百毫秒到几秒的延迟，且天然需要联网或算力。

这条分界线还有一个实际好处：**换模型、改人格、加工具都不需要重新烧录固件**。

## 3. 一次「你前面有什么」的完整旅程

这是理解整套框架最快的方式。

```
1. 用户说话 → 固件本地唤醒词命中 → 发 event: wake_word
2. runtime._voice_loop 收到事件（经事件总线）
3. robot.play_tone(880Hz)            即时反馈，让用户知道被听见了
4. robot.start_listen() → 固件开始上传 audio 分片
5. robot.collect_audio() → 攒够一段 PCM（静音超时或设备 end 结束）
6. asr.transcribe(pcm) → "你前面有什么东西"
7. agent.run(text)：
   7.1 组装 system prompt = 人格 + 当前设备状态（电量/能力/是否在动）
   7.2 provider.chat(messages, tools) → 模型返回 tool_call: look_around
   7.3 registry.execute("look_around") → tools.py 里的实现
        └─ robot.look() → command: snapshot
           └─ 固件回 frame(id=同一条命令) → 网关 base64 解码 → 帧缓存
        └─ vision.detect(frame) → VLM 返回「桌上有一个红色马克杯…」
   7.4 工具结果回喂模型 → 模型给出最终文本
8. robot.set_face(infer_emotion(reply))   自动表情
9. tts.synthesize(reply) → robot.say(wav) → 固件播放
```

关键设计点：

* **工具调用是模型决定的，不是硬编码的流程。** 第 7.2 步模型也可以选择
  直接回答（例如它认为不需要看图）。框架不干预这个决策。
* **设备状态每轮重建。** 电量、运动状态、在线能力都写进 system prompt，
  因为这些直接影响模型「该不该让它移动」。
* **失败被收敛成结果而不是异常。** 相机坏了、网络超时都会变成
  `{"ok": false, "error": "..."}` 回喂给模型，模型据此换策略或如实告知用户。

## 4. 六个核心设计决策

### 4.1 协议是唯一契约，且先于实现冻结

`docs/protocol.md` + `device/protocol.py` 是 PC 与固件之间唯一的接口。
好处是**两端可以并行开发**：固件同学照着文档写，PC 侧用
`mock_device/` 模拟设备端跑通全链路。`mock_device` 不是玩具——
它实现了完整的协议行为（含开环定时、音频分片、事件上报），
本项目里绝大多数 bug 就是靠它发现的。

### 4.2 「能力」而非「型号」决定行为

设备在 `hello` 里声明 `capabilities`。PC 侧据此：

* **过滤工具**：没有摄像头的设备，模型根本看不到 `look_around`，
  因此不会调用一个注定失败的工具；
* **钳制速度**：取 `hello.motor.max_linear` 与配置上限的较小值；
* **调整提示词**：明确告诉模型「本机没有麦克风」，避免它承诺做不到的事。

新增一种机器人（例如加机械臂）只需要在协议里加能力名和对应 action，
PC 侧的过滤与提示词逻辑不需要改。

### 4.3 工具描述就是提示词工程的主战场

模型只能看到工具名、描述、参数字段。所以 `brain/tools.py` 里每个
docstring 的第一句都回答「**什么时候该用它**」，而参数说明写清
单位、方向、取值范围：

```python
async def look_around(question: str = "", device_id: str = "") -> dict:
    """用摄像头看眼前的情况，返回识别到的物体和场景描述。

    这是你了解周围环境的主要方式。需要知道前面有什么、有没有障碍物、
    有没有人、能不能往前走时，都应该调用它，而不是凭猜测回答。
    """
```

这不是文档，这是**运行时输入**。

### 4.4 安全护栏在 PC 侧也做一层

设备固件必须自己做保护（见协议第 4 节），PC 侧再做一层，
因为模型可能给出任意数值：

* 速度/角速度钳制到 `max_linear_mps` / `max_angular_rps`；
* 单次运动时长上限 `max_duration_ms`（防止「一直往前冲」）；
* 运动指令最小间隔 `min_command_interval_ms`（抑制抖动伤齿轮箱）；
* **急停绕过模型**：`runtime.emergency_stop()` 直接走 intent 通道，
  不等 LLM 回复——安全逻辑不该排在推理后面。

### 4.5 反思与降级：机器人必须永远有反应

语音链路里任何一环失败，用户都必须能感知到：

| 故障 | 表现 |
|---|---|
| LLM 连不上 | 「我的大脑有点连不上，稍后再试试吧。」 |
| 视觉模型失败 | 工具回 `ok:false`，模型如实说做不到 |
| TTS 失败 | 仅屏幕显示文字，对话不中断 |
| 显示不响应 | 仅语音播报，对话不中断 |
| 设备掉线 | 仍允许纯文本对话（`get_status` 之类的工具始终可用） |

`Agent.run()` **不向上抛业务异常**——所有失败收敛进 `AgentTurn.error`。

### 4.6 离线假模型是框架的一部分，不是权宜之计

`llm/mock_provider.py` 让整个系统不需要 API key 就能跑通。
它的价值：

* 框架的每一环（协议、工具、安全、语音时序）都能在 CI 里稳定断言，
  不受模型随机性影响；
* 新协作者拉下代码 5 分钟就能看到机器人动起来；
* 真模型故障时可临时切回，机器人至少还能响应基本口令。

### 4.7 配置必须能在运行期改，但不该什么都能改

派机器人去现场调试时，最烦的是「为了换个模型 key 要重启整个服务」。
所以 `runtime.apply_config()` 支持**热重建 provider**：
改完配置立刻重建 LLM / 视觉 / ASR / TTS 实例，并把新引用同步给
已存在的 Agent 与工具上下文，旧对话历史照常保留。

但**不是所有配置都允许运行期改**。`config.EDITABLE_FIELDS` 是一份白名单，
只有登记过的字段能被 `/api/config` 读写。监听端口、CORS、WS 路径这些
启动期设置不在其中——它们改了也不会生效（uvicorn 已经绑定完了），
所以接口会**明确拒绝**而不是静默忽略。静默忽略比报错更糟：
用户以为改了，实际没生效，然后开始怀疑别的地方。

密钥的处理有一条容易忽略的约定：**前端拿到的是打码后的空串，
传空字符串表示「保持原值不变」**。否则用户每次只改模型名，
保存时都会顺手把已配置的 key 抹掉。要真正清空必须显式传 `null`。

控制台的「设置」页由 `app.py` 里的 `_CONSOLE_HTML` 提供（内联，
零构建步骤、零前端依赖），它通过 `/api/config`、`/api/config/test`
与 `config.EDITABLE_FIELDS` 驱动，因此加一个可配置项只需要在
`EDITABLE_FIELDS` 里登记一行 —— 前端会自动渲染出对应控件。

## 6. 线程与并发模型

全程单事件循环（asyncio），没有线程池用于业务逻辑。要点：

| 关注点 | 做法 |
|---|---|
| 发送串行化 | `DeviceConnection._send_lock`，防止并发任务交叉写坏 JSON 帧 |
| RPC 配对 | 每条 command 一个 `Future`，按 `id` 配对，超时抛 `DeviceTimeoutError` |
| 同一设备对话 | `Agent._lock` 串行化，避免两轮对话抢同一个底盘 |
| 高频媒体 | 有界队列 + 丢最旧。**慢消费者不该阻塞机器人动作** |
| 麦克风独占 | 模块级 `_RECORDING` 集合。语音闭环与 `listen` 工具不能同时采集 |
| 同步工具 | `asyncio.to_thread` 丢线程池，避免阻塞事件循环 |

**踩过的坑：一个 WebSocket 只能有一个消费者。** 早期在 `/robot` 路由里
同时挂了网关的接收循环和一个「探测断开」的监听协程，两个协程并发
`receive()` 会把消息随机分走，摄像头帧被静默丢弃且不报错。
现在断开检测内建在网关的接收循环里。

## 7. 已知限制与后续方向

当前实现有意留白的部分：

| 限制 | 说明 / 方向 |
|---|---|
| 无闭环运动 | `drive` 是开环定时的。要精确走 1 米需要轮式里程计反馈 |
| 无多机协同 | 协议与注册表支持多设备（工具都有 `device_id`），但 agent 是单机视角 |
| 无地图与导航 | 没有 SLAM、路径规划、避障决策。`obstacle` 事件已定义但 PC 侧只记录 |
| 对话历史无压缩 | 条数上限硬截断。长对话需要摘要或向量检索 |
| 视觉无连续跟踪 | 每次 `look_around` 是独立抓帧，不做目标跟踪 |
| 无鉴权 | 设备 WS 与 HTTP API 都无认证。**只应部署在可信内网** |
| 配置改动无审计 | `/api/config` 会写入 `.env`，但没有改动记录与回滚 |
| 音频不分片上传 | 采集是「攒完再送 ASR」，不是流式识别，首字延迟偏高 |

按性价比排序，最值得做的下一步：

1. **流式 ASR**：边采集边识别，显著降低语音响应延迟；
2. **轮式里程计闭环**：`drive` 带 `distance_m` 精确控制，协议已有 `imu` 字段可扩展；
3. **避障决策**：把 `obstacle` / `cliff` 事件接入安全层，急停 + 主动后退；
4. **对话摘要**：长对话压缩，替代硬截断。

## 8. 协议扩展指引

加一个新动作（例如「控制机械臂」）需要动的地方：

1. `device/protocol.py`：`Action` 枚举加一项；
2. `docs/protocol.md`：动作表加一行，注明所需能力与参数单位；
3. `device/capabilities.py`：`Robot` 加一个语义化方法（含能力校验与安全钳制）；
4. `brain/tools.py`：加一个工具函数，**docstring 第一句写清何时使用**；
5. `mock_device/device.py`：加 `_do_<action>` 方法（否则模拟设备会回
   `unsupported_action`，链路无法验证）。

固件侧对应实现该 action 并在 `hello.capabilities` 里声明新能力即可。
PC 侧的工具过滤、安全层、提示词都不需要改——这是第 4.2 节那个决策的红利。
